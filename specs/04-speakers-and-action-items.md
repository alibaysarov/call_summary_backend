# Spec 04 — Спикеры, извлечение и исправление задач

Модель-исполнитель: **GPT-5.6 Sol** (`gpt-5.6-sol`). При запуске выполнения
этого spec выбирать указанную модель; запись в документе сама модель не переключает.

Статус: запланировано. Зависимости: specs 01–03.
Источник: [IMPLEMENTATION_PLAN.md](../IMPLEMENTATION_PLAN.md), разделы
«Схема данных», «Извлечение задач и управление контекстом», «Приём и обработка».

## Результат и границы

Звонок даёт проверяемые поручения с ответственными, сроками и источниками.
Неопределённость сохраняется явно. Автоматическое узнавание голоса и подключение
аккаунтов сервисов не являются условием этого этапа.

## Что сделать

- Реализовать связи people/person_identities/meeting_participants/meeting_speakers
  и ручное подтверждение/исправление спикера. Все внешние ID API — UUID,
  внутренние FK/JOIN — BIGINT; доступ и связи ограничены workspace.
- Локальная метка SPEAKER_00 не связывает разные файлы. Одинаковые имена не
  объединяют людей/аккаунты. Подтверждённые person_identities можно использовать
  в следующих звонках; список присутствующих не идентифицирует голоса смешанной записи.
- Отдельный интерфейс LLM с типизированным и валидируемым результатом: создание
  поручения, уточнение, отмена, доказательства в репликах, неопределённость.
- Собирать контекст из нового временного окна, хвоста предыдущего диалога,
  подтверждённых участников и релевантных открытых задач. Задать бюджет токенов;
  длинный контекст разбивать и при необходимости подгружать дополнительные реплики.
- Обрабатывать окна последовательно внутри звонка с учётом готовности дорожек.
  Для mixed/per-person представлений анализировать выбранный primary-набор.
- Различать говорящего и ответственного; учитывать согласие в следующем файле.
  Не выдумывать assignee, due_at или статус done; review_status отражает сомнения.
- Сохранять deadline_text; относительную дату разрешать только с достаточной
  информацией о времени записи/часовом поясе. Дата загрузки её не заменяет.
- Записывать action_items и action_item_sources, проверяя существование и
  принадлежность реплик. Изменения записывать в action_item_events с предыдущими
  и новыми значениями; дать API корректировки ответственного, текста, срока и статуса.
- Разделить идемпотентность job и смысловое сопоставление поручений. Уточнение
  обновляет существующую задачу, разные поручения одному человеку не сливаются.
- Защитить ручные исправления от тихого перезаписывания повторным анализом:
  зафиксировать политику приоритета/проверки и проверить её на повторной обработке.
- Сбой LLM не теряет транскрипт. Финализация сверяет задачи с источниками окнами;
  поздние файлы запускают новую сверку с историей, не отменяя факт окончания звонка.
- Анализ использует сохранённые реплики PostgreSQL и не скачивает аудио заново
  из MinIO/Supabase. Источники задач ссылаются на реплики, не на постоянные публичные
  URL приватных аудиофайлов; смена S3 endpoint не меняет эти связи.

## Критерии оценки и проверки

| ID | Критерий приёмки | Как проверить |
| --- | --- | --- |
| S04-01 | Ответственный определяется по контексту | «Иван: Али, подготовь документ» + «Али: сделаю» в следующем файле даёт одну задачу Али с обеими репликами |
| S04-02 | Неопределённость сохраняется | Неизвестный спикер/неясный срок оставляют nullable поля и отметку проверки; «завтра» без даты записи не получает выдуманный due_at |
| S04-03 | Идентификация не основана на имени | Одинаковые имена в разных сервисах и SPEAKER_00 в разных файлах не сливаются; явная привязка работает |
| S04-04 | История договорённостей прослеживается | Смена срока и отмена изменяют исходную задачу и добавляют события с источниками; прошлые значения доступны |
| S04-05 | Retry не дублирует задачи | Повторить job и итоговый анализ; число поручений/источников не растёт без нового содержания |
| S04-06 | Разные представления не удваивают поручения | Подать mixed и per-person версии одного разговора, выбрать primary-набор и проверить единственный результат |
| S04-07 | Контекст ограничен | На длинном звонке измерить вход каждого LLM-вызова: бюджет соблюдён, вся история не передаётся, недостающий контекст дочитывается окнами |
| S04-08 | Сбой/невалидный ответ не повреждает данные | Имитировать timeout, неверные поля и ссылки на чужие реплики: текст сохранён, неверные задачи не записаны, retry доступен |
| S04-09 | Исправления устойчивы | Исправить задачу/спикера через API и повторить анализ: действует документированная политика, есть история, нет тихой потери правки |
| S04-10 | Изоляция workspace сохранена | Попытка назначения человека или источника из другого workspace отклоняется |

Использовать фиксированные диалоги и заглушки LLM для логики сохранения/повторов.
Для качества извлечения дополнительно подготовить размеченный набор: поручения,
уточнения, отмены, отсутствие задач и неоднозначность. На реальном LLM записать
пропуски/лишние задачи, корректность ответственного/срока и источников; не объявлять
семантическое качество проверенным только по результатам заглушки.

## Артефакты завершения

Сервисы идентификации/анализа/корректировки, схемы ответов LLM, политика контекста
и обновления задач, фикстуры и отчёт S04 с примерами ожидаемого/фактического результата.
