# Spec 06 — Репетиция переноса в Supabase

Модель-исполнитель: **GPT-5.6 Sol** (`gpt-5.6-sol`). При запуске выполнения
этого spec выбирать указанную модель; запись в документе сама модель не переключает.

Статус: запланировано. Зависимости: specs 01–05; для реальной репетиции нужны
тестовый проект Supabase и доступы, переданные через серверную конфигурацию.
Источник: [IMPLEMENTATION_PLAN.md](../IMPLEMENTATION_PLAN.md), разделы
«Перенос в Supabase», «Схема данных», «Решения и границы».

## Результат и границы

Проверенный перенос копии БД и аудио с сохранением идентификаторов, истории
миграций и работоспособности приложения. Рабочие данные локально не удаляются.
Supabase размещает PostgreSQL/Storage; Python API и worker размещаются отдельно.
Реальный cutover и embeddings не входят в обязательный результат репетиции.

## Что сделать

- Перед переносом сверить текущую официальную документацию подключения/миграции
  Supabase и совместимость версии PostgreSQL, расширений и клиентских утилит.
- Настроить DATABASE_URL и отдельный MIGRATION_DATABASE_URL, SSL и небольшой пул.
  Выбрать direct/session pooler по окружению; задокументировать фактический выбор.
- Проверить Alembic на пустой тестовой БД. Не создавать вторую историю миграций
  Supabase CLI, не заменять системные схемы/роли целевого проекта.
- Использовать S3-адаптер spec 03 с private Supabase Storage bucket, не вводить
  отдельную Supabase-only реализацию. Настроить endpoint, регион, credentials,
  SigV4/path-style по документации целевого проекта; сохранить storage_key.
- Серверные S3 access keys Supabase обходят RLS. Проверять доступ к объектам
  в backend по workspace и не передавать ключи клиенту/в логи.
- Обеспечить аутентификацию и членство в workspace до удалённого доступа.
  Если таблицы доступны через Data API, включить RLS по членству. Серверный
  доступ независимо от RLS также ограничивает каждый запрос workspace.
- Подготовить runbook: остановка приёма, завершение/учёт jobs и остановка worker,
  согласованный backup БД/аудио, перенос, проверка, смена конфигурации, возобновление.
  Репетицию выполнять на копии; состояние незавершённых jobs и leases учитывать явно.
- Не смешивать два способа создания одной схемы: отдельно проверить чистые
  migrations, затем для rehearsal выбрать согласованный restore схемы+данных
  либо загрузку данных в схему, созданную Alembic. История Alembic должна совпадать.
- Переносить id UUID и int_id BIGINT без регенерации, включая связующие таблицы.
  Для GENERATED ALWAYS использовать подходящий механизм загрузки и восстановить
  identity-последовательности после данных; все FK/JOIN остаются внутренними.
- Перенести аудио из MinIO в Supabase через S3 API с сохранением storage_key,
  MIME и нужных метаданных. Не копировать внутренний volume MinIO или файлы
  напрямую в backend Supabase: объекты должны регистрироваться через Storage API.
  Смена endpoint сама по себе данные не переносит.
- Сравнить перечень storage_key с пагинацией, размеры/SHA-256 и ссылки.
  ETag не считать универсальным хешем содержимого. Не зависеть от S3 versioning;
  резервная копия источника необходима для восстановления.
  Проверить количество строк, связи, статусы, расшифровки, задачи и источники.
- Подготовить возврат на локальную копию до возобновления записи. Если запись
  уже возобновлена в целевом окружении, сначала сохранить/сверить новые данные;
  простое переключение на старую копию не считать безопасным возвратом.
- Embeddings рассматривать только после оценки текстового поиска spec 05;
  решение и критерии улучшения оформить отдельно, не добавлять pgvector автоматически.

## Критерии оценки и проверки

| ID | Критерий приёмки | Как проверить |
| --- | --- | --- |
| S06-01 | Чистая схема разворачивается | Применить Alembic к пустой тестовой БД Supabase, сравнить ожидаемый head и ограничения |
| S06-02 | Данные перенесены без смены ID | Сравнить строки/UUID/int_id и связанные сущности исходной копии и назначения; проверить отсутствие orphan FK |
| S06-03 | Identity продолжает работать | После restore вставить новые строки в таблицы: нет конфликтов PK и изменений старых ID |
| S06-04 | Файлы доступны приложению | Сверить ключи/хеши и прочитать аудио через storage-интерфейс; bucket остаётся private |
| S06-05 | Сервисы работают на целевой БД | Через API загрузить тестовый файл, дождаться результата, прочитать задачи и источники через MCP |
| S06-06 | Доступ разделён | Проверить двух пользователей/workspace в API/MCP и Data API при его включении; чужие записи недоступны |
| S06-07 | Очередь корректна после переноса | Перенести копию с pending/просроченным job, возобновить worker: результат не потерян и не продублирован |
| S06-08 | Возврат воспроизводим | По runbook вернуть тестовое приложение на локальную копию до возобновления записи; подтвердить доступ к данным |
| S06-09 | Нет ложного объявления cutover | В отчёте отдельно указать тестовую БД, фактически проверенные шаги и оставшиеся действия реального переноса |
| S06-10 | Адаптер одинаков в обоих окружениях | Повторить S03-11 на MinIO и Supabase, меняя только конфигурацию; проверить используемые multipart-операции, если они включены |
| S06-11 | Объекты действительно перенесены | Сравнить полный список ключей, MIME, размеры и SHA-256 после копирования; прочитать объект из Supabase при выключенном MinIO |

Проверки запускаются на отдельном тестовом проекте. При отсутствии Supabase-доступа
подготовить скрипты/инструкции и локальный restore-тест, но отметить удалённую
репетицию невыполненной, не заменяя её локальным тестом в отчёте.

## Артефакты завершения

Проверенная конфигурация общего S3-адаптера, скрипт копирования объектов,
runbook backup/restore/cutover/возврата,
проверки целостности, отчёт S06 с фактическими результатами и перечнем ограничений.
