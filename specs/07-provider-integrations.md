# Spec 07 — Автоматические адаптеры сервисов

Модель-исполнитель: **GPT-5.6 Sol** (`gpt-5.6-sol`). При запуске выполнения
этого spec выбирать указанную модель; запись в документе сама модель не переключает.

Статус: будущий этап. Зависимости: specs 01–05; spec 06 нужен для выбранного
размещения в Supabase, но локальная проверка заглушек от него не зависит.
Источник: [IMPLEMENTATION_PLAN.md](../IMPLEMENTATION_PLAN.md), раздел
«Будущий этап: автоматический приём из разных сервисов».

## Результат и границы

Google Meet, Discord и Telegram подключаются по одному к общему ingestion-сервису.
Для каждого подтверждается конкретный рабочий режим. База данных и поле provider
сами по себе не означают готовую интеграцию. Загрузка по кнопке продолжает работать.

## Что сделать

- Сначала создать нормализованный контракт событий и заглушки: connection,
  event key, session key, event type, occurred_at, received_at, данные события.
  Затем реализовывать подтверждённые режимы сервисов по отдельности.
- Для каждого адаптера перед реализацией проверить актуальную официальную
  документацию, доступы и ограничения выбранной библиотеки/протокола. Зафиксировать
  поддерживаемые режимы: файл, готовая запись, события, живое аудио; не объявлять
  живой захват поддержанным по наличию webhook о начале звонка.
- Создавать подключения с transport=integration отдельно от каналов upload.
  Управлять подписками/курсорами и серверными secret_ref; не хранить токены в payload.
- Webhook проверяет подлинность и определяет workspace по подключению; событие
  и job сохраняются атомарно до подтверждения получения. Poll/stream используют
  тот же ingestion-сервис. Ключ и отпечаток события дают дедупликацию/конфликт.
- Сохранять события до появления звонка; worker позже разрешает source_session.
  Обрабатывать start/end/participant/file-ready не по порядку, без возврата end в active.
- Курсор продвигать после надёжного сохранения, подписки продлевать заданиями.
  После reconnect сверять доступную историю; невосстановимые пропуски помечать.
- Отличать внешний сеанс от комнаты. Повторный звонок в комнате создаёт новую
  сессию; reconnect текущего сохраняет её. Если внешнего session ID нет, сохранять
  устойчивый локальный ключ. Не склеивать источники по имени/времени автоматически.
- Сохранять внешние ID как TEXT с областью уникальности; все собственные таблицы
  имеют UUID id и BIGINT int_id, FK/JOIN используют int_id и workspace.
- Записывать участников, отдельные входы/устройства и подтверждённые аккаунты.
  Имена не подтверждают личность. Персональная дорожка может идентифицировать речь
  только при подтверждающих данных протокола; смешанная требует сопоставления.
- Отображать источники на audio_streams: поколение потока после сброса sequence,
  смещения относительно звонка, mixed/per-person и выбор primary-представления.
- Импортировать готовую запись через общий storage/worker и разбиение на фрагменты.
  Время импорта отделять от времени записи; поздние файлы запускают сверку задач.
- Все адаптеры сохраняют аудио через единый S3-слой: MinIO локально, Supabase
  Storage после переноса. Не вводить отдельные файловые каталоги/хранилища для
  каждого provider и не обходить правила ключей, приватности и workspace.
- Ограничить payload по размеру/сроку хранения, ретраи и нагрузку каждого адаптера.
  Ошибка одного подключения не должна останавливать другие или ручную загрузку.

## Режимы для проверки по сервисам

| Провайдер | Первый кандидат на реализацию | Что проверить отдельно |
| --- | --- | --- |
| Google Meet | События конференции и импорт доступной готовой записи | Доступ к артефактам, участникам и время готовности; live-аудио не входит автоматически |
| Discord | Voice-клиент и доставка аудио в общий pipeline | Актуальный протокол, поддержка приёма библиотекой, reconnect и привязка дорожки участнику |
| Telegram | Аудио/voice-файлы, отправленные боту | Дедупликация сообщений и явная привязка к звонку; живые звонки — отдельная проверка API/клиента |

Голосовое сообщение Telegram не объединять со всеми сообщениями чата в один
звонок. Создавать отдельную сессию импорта либо использовать явно выбранный meeting.

## Критерии оценки и проверки

| ID | Критерий приёмки | Как проверить |
| --- | --- | --- |
| S07-01 | Общий контракт работает до реальных доступов | Прогнать заглушками жизненный цикл, участников и файл: получена общая цепочка до задач |
| S07-02 | Доставка событий идемпотентна | Повтор webhook, конкурентная доставка и retry после restart дают одно событие/сеанс/job; иной payload с тем же ключом — конфликт |
| S07-03 | Порядок событий не ломает состояние | End раньше start, файл до создания звонка, поздний артефакт: состояние и итоговая сверка корректны |
| S07-04 | Сеанс не равен комнате | Два звонка в комнате различаются, reconnect текущего не создаёт новый; локальный session key переживает restart |
| S07-05 | Подписки восстанавливаются | Заглушкой проверить expiry/renew, отказ сохранения перед продвижением cursor и восстановление после reconnect |
| S07-06 | Участники и дорожки согласованы | Повторные входы/устройства сохранены; сброс нумерации сохраняет время; mixed/per-person не удваивают задачи |
| S07-07 | Аккаунты не смешиваются | Равные имена не объединяют людей, подтверждённые идентичности дают задачи одного человека со всех подключённых источников |
| S07-08 | Доступы проверяются | Неподлинное событие и межпространственные ссылки отклоняются; payload/логи не содержат секретов |
| S07-09 | Реальный режим доказан отдельно | Для каждого сервиса выполнить небольшой реальный звонок/импорт/voice-сообщение в заявленном режиме и проверить текст, время, источники, задачи |
| S07-10 | Сохраняется работа других входов | При падении адаптера загрузить file+provider по кнопке и обработать событие другого подключения |

Заглушки проверяют устойчивость, реальные прогоны — возможности сервиса.
При недоступных ключах/режиме указывать «не проверено/не поддерживается», не считать
адаптер завершённым по одной модели БД. Статус приёмки вести отдельно для каждого
из трёх сервисов; этап целиком готов после проверки согласованных режимов всех трёх.
