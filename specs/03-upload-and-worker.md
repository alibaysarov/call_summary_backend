# Spec 03 — Загрузка по кнопке, очередь и worker

Модель-исполнитель: **GPT-5.6 Sol** (`gpt-5.6-sol`). При запуске выполнения
этого spec выбирать указанную модель; запись в документе сама модель не переключает.

Статус: запланировано. Зависимости: [spec 01](01-infrastructure-and-data-model.md),
[spec 02](02-structured-transcription.md).
Источник: [IMPLEMENTATION_PLAN.md](../IMPLEMENTATION_PLAN.md), разделы
«Текущий сценарий: загрузка по кнопке», «Приём и обработка», «API и последующий MCP».

## Результат и границы

Один запрос с файлом и provider создаёт звонок и запускает надёжную фоновую
обработку. Реальные боты, подписки и захват сервисов относятся к spec 07.
Извлечение задач подключается через контракт следующего задания в spec 04.

## Что сделать

- Реализовать `POST /audio`, multipart/form-data: file и provider. Допустимы
  manual/google_meet/discord/telegram; пропуск означает manual, неизвестный код — 422.
- Workspace брать из контекста доступа, локально использовать один workspace.
  Сервер сам создаёт/находит upload-канал и создаёт meeting, source_session,
  audio_stream, audio_chunk и job; предварительных запросов от кнопки не требуется.
- Все четыре provider использовать с transport=upload без OAuth/ботов. Это метка
  происхождения; ASR-провайдер остаётся серверной настройкой. Локальные account/scope
  и session key не выдавать за подтверждённые внешние идентификаторы.
- Возвращать 202: публичные UUID meeting_id, stream_id, chunk_id, status, status_url.
  Реализовать `GET /meetings/{id}` и состояние фрагмента, включая ошибки и полноту.
  Внутренние int_id клиенту не передавать; JOIN и FK используют BIGINT.
- Законченный файл по умолчанию создаёт новый звонок: первый chunk имеет sequence_no=0,
  offset_ms=0. При разбиении длинной записи определить устойчивые границы/номера,
  возвращённый chunk_id сохранить за первым фрагментом; status_url относится ко всему
  звонку. Заполнить число фрагментов и закрыть источник после определения длительности.
  Неизвестное календарное время записи оставить NULL.
- Поддержать Idempotency-Key через integration_events канала upload и отпечаток
  файла/provider/метаданных. Повтор возвращает прежние ID, изменённое содержимое — 409.
  Без ключа и meeting_id — новая отправка, даже если хеш и provider совпадают.
- Добавить режим фрагментов: meeting_id, stream_id, sequence_no, offset_ms, is_final.
  Первый is_final=false может создать сущности автоматически; продолжение использует
  возвращённые UUID. Проверять согласованность provider, workspace и принадлежности.
- Добавить расширенные операции создания звонка/дорожки, загрузки фрагмента и finish
  из плана как обёртки одного сервиса. Finish идемпотентен.
- Реализовать один S3-адаптер для локального MinIO и будущего Supabase Storage:
  put/get/download/head/delete/list с пагинацией. Endpoint/регион/bucket/ключи,
  SigV4 и path-style настраиваются окружением. S3 credentials только серверные.
- Использовать приватный bucket и переносимый storage_key с UUID workspace,
  meeting, stream, chunk. Проверять размер/формат и SHA-256, не полагаться на ETag.
  Приложение не читает volume MinIO; worker скачивает аудио в AUDIO_TEMP_DIR
  и убирает временный файл после успеха/ошибки. Ограничить память и временный диск.
- Надёжно сохранять объект до подтверждения, затем атомарно сохранять строки/job.
  S3 и БД не имеют общей транзакции: предусмотреть компенсацию/повтор и orphan-уборку
  с периодом ожидания и учётом активной обработки. Конкурентный retry не должен
  перезаписать/удалить объект победившего запроса; стратегия владения объектом
  и очистки должна быть явной. Проверять конфликт содержимого до перезаписи.
- Ограничиться общими S3-операциями, не зависеть от versioning/MinIO notifications.
  Если используется multipart, проверить его совместимость и abort незавершённых
  загрузок. Синхронный S3-клиент не должен блокировать event loop.
- Очередь PostgreSQL: короткий захват `FOR UPDATE SKIP LOCKED`, обработка вне
  транзакции, lease/heartbeat/lease_token, ограниченные retry с задержкой и явный retry
  после failed. Не добавлять Redis/Celery в MVP.
- Атомарно сохранять реплики, result_text, статус и следующее задание. Retry и
  повторная доставка не размножают записи; stale worker не фиксирует результат.
- Реплики хранить на шкале звонка; sequence_no уникален только внутри stream.
  Сброс нумерации создаёт новую дорожку. Учитывать пропуски, порядок поступления,
  выбранные primary-дорожки и задержанные файлы. Финализация отличает конец записи
  от завершения обработки; неизвестная полнота указывается явно.
- Подготовить последовательный анализ временных окон с границей готовности дорожек
  и ограниченным ожиданием; фактический анализ поручений реализует spec 04.
- Ограничить параллелизм и расход памяти, обеспечить восстановление worker после
  restart и отсутствие тяжёлой работы в API event loop. Завершить выбранный в
  spec 02 способ обслуживания старого /transcribe.
- Измерять длительность обработки, очередь/отставание и ошибки. Учитывать сумму
  активных звонков/дорожек и не допускать монополизации очереди одним источником.

## Критерии оценки и проверки

| ID | Критерий приёмки | Как проверить |
| --- | --- | --- |
| S03-01 | Минимальная загрузка работает | Для четырёх provider отправить file+provider без других вызовов; проверить 202, UUID, цепочку записей и результат по status_url |
| S03-02 | Вход валидируется | Пропуск provider даёт manual, неизвестный — 422; чужие/несогласованные ID отклоняются, ASR не меняется |
| S03-03 | Идемпотентность выдерживает конкуренцию | Одновременные запросы с одним ключом дают одну цепочку; иной файл с тем же ключом — 409; без ключа два запроса дают два звонка |
| S03-04 | Фрагменты объединяются корректно | Три файла с сохранёнными ID, в том числе не по порядку, дают один звонок с правильной хронологией |
| S03-05 | Несколько дорожек независимы | Оба stream принимают номер 0; сброс нумерации в новой дорожке не сбрасывает время звонка |
| S03-06 | Завершение не теряет данные | Проверить полный файл, длинный файл с разбиением, is_final=false/true, повтор finish, пропуск, поздний файл и неизвестное количество |
| S03-07 | Worker восстанавливается | Остановить процесс после захвата/после вычисления/перед commit; возобновить: данные не теряются и не дублируются |
| S03-08 | Lease защищает результат | Просрочить lease, передать job другому worker; первый с устаревшим токеном не может зафиксировать данные |
| S03-09 | Ошибки контролируемы | Сбой storage/БД/ASR, тишина и исчерпание retry дают правильный статус, очистку и возможность восстановления |
| S03-10 | Поток выдерживает измеренную нагрузку | Подавать минутное аудио раз в минуту, затем несколько потоков; записать конфигурацию, throughput, длительности, рост очереди и отставание |
| S03-11 | S3-контракт переносим | На реальном MinIO проверить put/get/head/delete/list, несколько страниц объектов, отсутствующий ключ, совпадение байтов/SHA-256 и приватность bucket; тот же набор повторяется в spec 06 |
| S03-12 | Сбои не повреждают объекты | Имитировать upload success + DB failure, timeout S3 и конкурентный retry; проверить компенсацию, отложенную уборку и сохранность используемых объектов |
| S03-13 | Временное аудио очищается | Успех/ошибка ASR и прерванная обработка не оставляют бесконтрольных временных файлов; повтор скачивает исходный S3-объект |

Тесты очереди и конкуренции выполняются на PostgreSQL с заглушками провайдеров.
Реальную скорость измерять отдельно; не считать скорость заглушки скоростью ASR.
Если очередь не успевает за входным потоком, документировать предел и настроить
worker/параллелизм до заявленной рабочей конфигурации, без неподтверждённых SLA.

## Артефакты завершения

Endpoint/сервисы upload, storage, worker, статусы и retry, инструкции кнопки/curl,
восстановления и диагностики, результаты S03 и нагрузочного прогона. Сквозная
финализация задач будет завершена в spec 04, а не отмечена готовой заранее.
