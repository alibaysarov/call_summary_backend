# Задание: хранение и обработка звонков

Статус: spec 01 реализован и проверяется локально; specs 02–07 запланированы.
Фактические результаты: [отчёт S01](docs/spec01-verification.md).

## Цель

На первом этапе принимать аудиофайл по нажатию кнопки на клиенте.
Минимальный запрос содержит файл и `provider`; создание записей выполняет сервер.
В дальнейшем принимать аудио примерно раз в минуту, объединять фрагменты в звонки,
сохранять расшифровку с репликами и извлекать поручения. Отвечать через MCP
на вопросы вроде «Что Али нужно сделать после звонка?» без передачи всей
истории разговоров в контекст модели.

Первое окружение — локальный Docker Compose. Следующее — PostgreSQL в
Supabase и Supabase Storage для аудио. Локально аудио хранится в MinIO,
приложение использует один S3-адаптер для обоих окружений.

Архитектура должна поддерживать автоматическое поступление звонков из разных
сервисов: Google Meet, Discord, Telegram и будущих интеграций. Сначала реализовать
общую модель и адаптер загрузки файлов; подключение реальных сервисов — отдельными
этапами, без изменения основных таблиц при добавлении очередного провайдера.

## Решения и границы

- Основное хранилище — обычные связанные таблицы PostgreSQL.
- В MVP нет графовой БД, embeddings и отдельного векторного сервиса.
- Python API и worker работают в контейнерах. Supabase используется для БД
  и хранения файлов; размещение Python-контейнеров планируется отдельно.
  Перенос данных в Supabase не означает перенос туда процесса VoiceProcessor.
- Docker локально не означает полностью офлайн: текущие провайдеры Deepgram
  и будущий LLM могут требовать сеть и ключи. Провайдеры задаются конфигурацией.
- Существующий `POST /transcribe` с ответом `{"text": ...}` сохраняет совместимость.
- Основной новый сценарий — `POST /audio` с файлом и provider. Автоматические
  подписки, боты и захват звонков не являются условием готовности первого MVP.
- SQLAlchemy + PostgreSQL-драйвер для доступа к БД, Alembic как единственный
  источник миграций. Alembic уже указан в `pyproject.toml`.
- Не создавать параллельную историю миграций через Supabase CLI.
- Версию PostgreSQL закрепить в Compose и проверить совместимость с целевым
  проектом Supabase перед переносом. Образ `latest` не использовать.

## Что учесть в текущем коде

- `src/server.py` вызывает `VoiceProcessor.process_ogg()` и возвращает строку.
- В `src/call_summary/voice_sherpa_persistent.py` доступны текстовые сегменты
  и результаты диаризации до вызова `merge_transcript_with_speakers()`.
- Ввести структурированный результат обработки: реплики, временные метки,
  локальная метка спикера и форматированный текст для старого API.
  Не восстанавливать реплики разбором готового `result_text`.
- Проверить и унифицировать точку запуска: есть `src/server.py` и
  `src/call_summary/server.py`, а Makefile использует `server:app`.

## Локальная инфраструктура

- `compose.yaml`: `db`, `minio`, `api`, `worker`; отдельные одноразовые команды
  миграций и идемпотентной инициализации приватного bucket/доступа к нему.
- Закрепить проверенный образ MinIO по версии/digest, не latest. Проверить
  доступность сборки, команды запуска и healthcheck до фиксации образа.
- Named volumes `postgres_data` и `minio_data`: второй монтируется только в MinIO.
  API/worker обращаются к аудио по S3; общий файловый volume между ними не нужен.
  Для конвертации и ASR worker использует собственные временные файлы с очисткой.
- Healthcheck БД и MinIO, readiness загрузки с проверкой БД и доступности bucket,
  ограниченный пул соединений. Отказ S3 не должен блокировать чтение сохранённых
  текстов/задач: проверку готовности чтения отделить от готовности загрузки.
- Отдельная загрузка моделей в worker; для совместимого `/transcribe`
  предусмотреть делегирование worker либо явно описать отдельный режим запуска.
  MCP и чтение задач не должны требовать загрузки речевых моделей.
- Ограничить параллелизм тяжёлой обработки; не выполнять её в event loop API.
- `.env.example`: DATABASE_URL, MIGRATION_DATABASE_URL, AUDIO_STORAGE_BACKEND=s3,
  S3_ENDPOINT_URL, S3_REGION, S3_BUCKET, S3_ACCESS_KEY_ID, S3_SECRET_ACCESS_KEY,
  S3_ADDRESSING_STYLE=path, AUDIO_TEMP_DIR, ключи и настройки провайдеров,
  лимиты файлов и worker. Настройки администратора MinIO отделить от учётных
  данных приложения; приложение использует доступ только к своему bucket.
  Реальные ключи, записи звонков и данные volumes не добавлять в Git.
- Команды Makefile: поднять окружение, применить миграции, посмотреть логи,
  остановить без удаления данных. Удаление volumes — отдельная явная команда.
- Проверить сборку с текущим Python >=3.14 и системными аудиозависимостями.
  Базовый сценарий CPU; GPU — отдельная документированная конфигурация.

## Хранение аудио: MinIO и Supabase Storage

```text
Кнопка → API → PostgreSQL (метаданные и очередь)
           → S3-адаптер → MinIO локально / Supabase Storage после переноса
Worker → очередь PostgreSQL → S3-адаптер → временный файл → ASR → реплики и задачи
ChatGPT → MCP → сервисы чтения → PostgreSQL
```

- Один интерфейс хранилища и одна S3-реализация для MinIO и Supabase Storage:
  put, get/download, head, delete, list с пагинацией. Выбрать совместимый Python
  S3-клиент; синхронные сетевые вызовы не выполнять в event loop.
- Приватный bucket, например `call-audio`. `storage_key` — относительный ключ
  `<workspace_uuid>/<meeting_uuid>/<stream_uuid>/<chunk_uuid>.ogg` с расширением
  фактического формата. Не хранить в нём URL endpoint, секрет или путь контейнера.
- Endpoint, регион, bucket и credentials задаются окружением; путь адресации
  и подпись SigV4 проверить с обоими endpoint. Внутри Compose endpoint имеет вид
  `http://minio:9000`; с хоста адрес задаётся отдельно, а не зашивается в код.
- Файлы не хранятся в PostgreSQL. В audio_chunks остаются ключ, SHA-256, MIME,
  длительность и result_text. Постоянные данные лежат в S3, локальные файлы —
  только временный этап загрузки/декодирования и удаляются при успехе/ошибке.
- DB и S3 не имеют общей транзакции: upload объекта, затем фиксация записей/job;
  при отказе — компенсация/повтор и уборка orphan-объектов. Ключи уникальны,
  повтор запроса не перезаписывает чужое содержимое и не удаляет объект победившего
  конкурентного запроса. Уборка учитывает активные загрузки/jobs и период ожидания.
- Использовать только проверенные общие S3-операции. Не зависеть от versioning,
  object lock, уведомлений MinIO или от ETag как эквивалента SHA-256.
  Если нужны multipart upload, проверить их отдельно и очищать незавершённые загрузки.
- Серверные S3-ключи Supabase обходят RLS; разрешение доступа проверяет backend
  по workspace. Не передавать их клиенту, в MCP-ответы или логи.
- При переносе скопировать объекты через S3 API с сохранением ключей и проверить
  число/размеры/SHA-256. Смена endpoint не переносит файлы. Не копировать внутренний
  volume MinIO в Supabase и не записывать объекты в обход Supabase Storage API.

Официальные ориентиры для реализации S3:

- [Supabase S3 compatibility](https://supabase.com/docs/guides/storage/s3/compatibility)
- [Supabase S3 authentication](https://supabase.com/docs/guides/storage/s3/authentication)
- [S3 и MinIO в self-hosted Supabase](https://supabase.com/docs/guides/self-hosting/self-hosted-s3)

## Схема данных

Для каждой таблицы, включая связующие и будущие таблицы, обязательны два поля:

- `id UUID NOT NULL UNIQUE DEFAULT gen_random_uuid()` — публичный идентификатор
  для API, MCP и внешних ссылок.
- `int_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` — внутренний
  идентификатор для всех внешних ключей и JOIN.

Все FK имеют тип BIGINT и ссылаются на `int_id` родительской таблицы.
Имена FK сохраняют вид `meeting_id`, `chunk_id`, `assignee_id` и т. п.;
в таблицах это внутренние BIGINT, а в HTTP/MCP входах и ответах — публичные UUID.
Сервисный слой явно преобразует публичные UUID во внутренние ключи и обратно;
внутренние ключи не выдаются клиенту. JOIN по UUID не использовать.
При переносе данных сохранять оба идентификатора и восстанавливать состояние
identity-последовательностей, чтобы новые записи не конфликтовали с перенесёнными.

TIMESTAMPTZ для календарного времени, целые миллисекунды для положения внутри
звонка. Текст хранится в TEXT; JSONB —
только для дополнительных метаданных, не вместо связей и основных полей.

`provider` — строковый код (`manual`, `google_meet`, `discord`, `telegram`),
проверяемый реестром адаптеров приложения. Отдельные таблицы звонков для каждого
сервиса не создавать. Внешние идентификаторы хранить как TEXT: их формат и область
уникальности определяет провайдер; они не являются FK нашей БД.

Разделить происхождение и способ доставки: `provider=discord` с `transport=upload`
означает файл, отправленный по кнопке и помеченный как запись Discord.
Это не подключённый Discord-бот и не подтверждённые сервисом метаданные.
Для будущего подключения используется отдельная запись с transport=integration.
Источник source_sessions.ingestion_mode описывает режим конкретного сеанса:
`file_upload`, `chunk_upload`, `recording_import` или `live_capture`.

`result_text` хранить на уровне фрагмента. Полную расшифровку звонка собирать
из реплик по времени при запросе или экспорте, не переписывать большую строку
каждую минуту. Аудио — в хранилище файлов; в БД только ключ и метаданные.

Ограничения и индексы:

- UNIQUE `(stream_id, sequence_no)` для аудиофрагментов: несколько дорожек
  одного звонка могут одновременно прислать фрагмент № 0.
- UNIQUE `(workspace_id, provider, transport, external_scope, external_account_id)`
  для подключений; scope/account обязательны, для manual задаются локальные значения.
- UNIQUE `(connection_id, resource_key)` для подписок и `(connection_id,
  deduplication_key)` для событий. При повторе сравнивать нормализованное содержимое;
  разные данные с одним ключом отмечать конфликтом, а не молча перезаписывать.
- UNIQUE `(connection_id, external_session_id)` для сеансов; если сервис не даёт
  ID сеанса, адаптер один раз создаёт и сохраняет собственный устойчивый ключ.
- UNIQUE `(workspace_id, provider, identity_scope, external_user_id)` для аккаунтов
  людей; identity_scope обязателен и отражает область уникальности ID провайдера.
- UNIQUE `(source_session_id, external_participant_id)` для участников,
  `(participant_id, external_join_id)` для входов,
  `(source_session_id, external_stream_key)` для дорожек.
- UNIQUE `(chunk_id, local_label)` для локальных спикеров.
- UNIQUE `(chunk_id, ordinal)` для реплик.
- Индекс `utterances(workspace_id, meeting_id, start_ms, int_id)` для хронологии.
- Индексы `action_items(workspace_id, assignee_id, status, meeting_id)` и
  `action_items(workspace_id, meeting_id, created_at, int_id)`.
- Индексы `meetings(workspace_id, started_at, int_id)`,
  `source_sessions(workspace_id, meeting_id)` и
  `integration_events(connection_id, received_at, int_id)`.
- UNIQUE `processing_jobs(workspace_id, deduplication_key)`; индекс очереди по
  status и available_at. CHECK по kind определяет обязательный FK: ingestion
  использует integration_event_id, transcription — chunk_id, finalization — meeting_id,
  poll/renew_subscription — subscription_id.
- CHECK для неотрицательных смещений, корректных интервалов и допустимых статусов.
- Внешние ключи и проверки согласованности: реплика и её фрагмент принадлежат
  одному звонку, источник задачи относится к тому же звонку.
- Все связи ограничены одним workspace: UNIQUE `(workspace_id, int_id)` на
  родительских таблицах и составные FK `(workspace_id, parent_id)` на дочерних.
  Сам workspace_id ссылается непосредственно на `workspaces.int_id`.
  Между ними JOIN выполняется по workspace_id и внутренним BIGINT-ключам.
  Дополнительно обеспечить соответствие meeting_id цепочке stream → source_session
  через составные ограничения либо constraint triggers в миграциях.
  В spec 01 это реализовано составными FK и triggers: ключи принадлежности
  неизменяемы после INSERT, атрибуция человека/спикера допускает UPDATE.
  Событие можно связать с source_session один раз; связь проверяется с его jobs.

Метка `SPEAKER_00` имеет смысл только внутри исходного фрагмента. Не связывать
автоматически одинаковые метки разных файлов с одним человеком. MVP допускает
ручное подтверждение соответствий и неизвестного ответственного; автоматическое
узнавание голоса — отдельная последующая задача.

## Текущий сценарий: загрузка по кнопке

Клиент отправляет один запрос `POST /audio` с телом `multipart/form-data`:

```text
file: <аудиофайл>
provider: manual | google_meet | discord | telegram
```

Для multipart файл и provider — поля тела запроса, не JSON с бинарным аудио.
Если provider не передан, использовать manual; неизвестное значение — `422`.
Provider определяет происхождение звонка, а не модель транскрипции:
настройки Deepgram/Whisper/LLM остаются серверными.

Пример будущего API (endpoint пока не реализован):

```bash
curl -X POST http://localhost:8010/audio \
  -F 'file=@recording.ogg' \
  -F 'provider=discord'
```

Без дополнительных параметров каждый успешный запрос создаёт отдельный звонок.
Сервер сам определяет workspace из контекста доступа (локально — один workspace),
находит/создаёт канал upload указанного provider, создаёт meeting, source_session,
audio_stream, сохраняет файл и ставит обработку в очередь. Для канала upload
использовать зарезервированные локальные account/scope; секреты и OAuth не нужны.
Ключ сеанса генерируется локально и не выдаётся за внешний ID сервиса.
Предварительно создавать звонок, подключение или дорожку на клиенте не требуется.

В ответе `202` вернуть публичные UUID meeting_id, stream_id, chunk_id,
status и status_url для проверки состояния. Для небольшого файла создать один
фрагмент с sequence_no=0, offset_ms=0; при разбиении длинного файла worker создаёт
остальные фрагменты с устойчивой нумерацией. Возвращённый chunk_id обозначает
первый фрагмент; status_url ведёт на состояние всего звонка. После получения
длительности заполнить expected_chunk_count и закрыть источник загрузки;
финализировать звонок после обработки всех фрагментов. Время загрузки не считать
временем записи: неизвестные started_at/ended_at оставить NULL.

Необязательный заголовок `Idempotency-Key` генерируется клиентом для одной отправки
и повторно используется при сетевом retry. Сохранить ключ через integration_events
канала upload с префиксом типа операции и отпечатком файла/provider/метаданных;
повтор возвращает исходные ID, отличающееся содержимое с тем же ключом — `409`.
Отсутствие ключа означает новую отправку: один лишь хеш аудио не объединяет звонки.
Для повторной попытки без provider в теле правила значения по умолчанию те же.

Будущий режим фрагментов использует тот же вход, но добавляет технические поля
meeting_id, stream_id, sequence_no, offset_ms и is_final. Первый фрагмент с
is_final=false может создать звонок/дорожку автоматически; при продолжении клиент
передаёт полученные ID и остальные поля. Без is_final запрос считается загрузкой
законченного файла. Проверять принадлежность ID и совпадение provider; некорректное
или неоднозначное сочетание полей отклонять. Клиент сохраняет ID между отправками
сам: пользователю не нужно вводить их вручную. Один provider не позволяет отличить
продолжение звонка от нового звонка или разделить два одновременных звонка.

## Будущий этап: автоматический приём из разных сервисов

Модель связей:

```text
workspace → integration_connection → source_session → audio_stream → audio_chunk
workspace → meeting ← source_session
person ← person_identity ← meeting_participant → participant_session
meeting → utterance → action_item_sources ← action_item
```

Это схема связей реляционных таблиц, не отдельная графовая БД.

- `meeting` — смысловой звонок; `source_session` — его конкретный внешний сеанс.
  Один звонок может иметь несколько источников при явном связывании. Совпадение
  названия, ссылки комнаты или времени само по себе не основание для объединения.
- ID комнаты/канала не является ID звонка: повторные встречи в одной комнате
  создают разные сеансы и звонки. Перезапуск адаптера в текущем сеансе использует
  сохранённый ключ и не создаёт новый звонок.
- `person` — человек в рабочем пространстве; его Google/Discord/Telegram аккаунты
  связываются через `person_identities`. Совпадение имени не подтверждает личность.
  Подтверждённые привязки аккаунтов можно повторно использовать в следующих звонках.
- Участник звонка и говорящий различаются. Для дорожки конкретного пользователя
  адаптер может подтвердить источник речи по данным протокола. Для смешанной записи
  список присутствующих не доказывает соответствие голосов именам.
- `participant_sessions` сохраняет повторные входы и несколько устройств.
  Если провайдер не выдаёт join ID, адаптер создаёт устойчивый локальный ключ.
- `audio_streams` отделяет параллельные дорожки и поколения потока после сброса
  нумерации. При сбросе sequence_no создать новую дорожку, сохранив общую шкалу
  времени. offset_ms реплики/фрагмента всегда относительно начала звонка;
  timeline_offset_ms хранит начало дорожки на этой шкале.
- Одновременные дорожки людей объединяются по времени. Смешанная запись и её
  отдельные дорожки — альтернативные представления: is_primary выбирает набор
  для анализа, чтобы одна речь не давала двойные реплики/поручения. Проверять
  отсутствие дублирующих представлений в выбранном наборе.
- Каждый адаптер преобразует события в общий контракт: connection, event key,
  session key, event type, occurred_at, received_at и нормализованные данные.
  Webhook, периодический опрос и потоковый клиент используют один ingestion-сервис.
- Проверить подлинность входящего события, записать его и задание атомарно,
  затем подтвердить получение. Повторы, задержанные события и изменение их
  порядка не должны создавать дубли или возвращать завершённый сеанс в active.
- Событие может прийти до создания звонка: integration_events и ingestion jobs
  допускают отсутствующий meeting/source_session. Worker разрешает связь позже.
- Сохранять курсор опроса после надёжной записи событий; продлевать истекающие
  подписки через задания. После разрыва соединения выполнять сверку доступной
  истории, а если восстановить аудио нельзя — отмечать неполноту.
- OAuth/bot-токены не хранить в settings/payload; secret_ref указывает на
  серверное хранилище секретов. Локально — переменные окружения. Объём и срок
  хранения сырых payload ограничить; поля для поиска хранить отдельно от JSONB.

Возможности адаптеров проверять отдельно, не обещать минутное аудио от любого API:

| Адаптер | Планируемый режим |
| --- | --- |
| `manual` | Загрузка файла/минутных фрагментов, базовый локальный MVP |
| `google_meet` | События конференции и импорт доступной готовой записи; получение живого аудио — отдельная проверка возможностей и доступа |
| `discord` | Отдельный voice-клиент для аудио; перед реализацией проверить протокол, библиотеку и поддержку приёма выбранным клиентом |
| `telegram` | Приём отправленных боту аудио/voice-файлов; захват живого звонка — отдельная интеграция, не предполагать его наличие в Bot API |

Готовую запись можно разбить на фрагменты локально после загрузки. Исходный
момент записи и время импорта различаются. Голосовое сообщение Telegram само
по себе не является звонком: привязывать к явно выбранному meeting либо создавать
отдельную сессию импорта; не объединять весь чат в один звонок.

Ориентиры для реализации адаптеров:

- [Google Meet: конференции, участники и артефакты](https://developers.google.com/workspace/meet/api/guides/overview)
- [Discord: Voice connections](https://docs.discord.com/developers/topics/voice-connections)
- [Telegram Bot API: сообщения и события](https://core.telegram.org/bots/api)

## Приём и обработка

1. Создать/найти звонок, source_session и audio_stream в текущем workspace.
   Для загрузки по кнопке сервер делает это по provider с transport=upload;
   для интеграции — обработчик нормализованного события.
2. В простом режиме клиент отправляет только файл и provider; сервер задаёт
   идентификаторы и параметры фрагмента. В режиме продолжения клиент дополнительно
   отправляет meeting_id, stream_id, sequence_no и offset_ms. Смещение берётся
   из записи, а не из времени прихода HTTP-запроса; длина не обязана быть ровно 60 с.
3. API проверяет ограничения, надёжно сохраняет файл, затем в одной транзакции
   создаёт фрагмент и задание. Возвращает `202` с chunk_id и статусом.
   При ошибке БД удаляет ненужный файл; предусмотреть уборку оставшихся orphan-файлов.
4. Повтор той же последовательности внутри дорожки с тем же содержимым и метаданными возвращает
   существующий фрагмент; с другим содержимым или смещением — `409`.
5. Worker забирает задания короткой транзакцией с `FOR UPDATE SKIP LOCKED`.
   Транскрипцию выполняет вне транзакции; lease, heartbeat и токен владения
   предотвращают запись результата устаревшим worker после повторного захвата.
6. Реплики, текст, статус и следующее задание сохраняются атомарно.
   Повтор выполнения не создаёт дубликаты реплик и задач.
7. Ошибка сохраняется с безопасным сообщением, выполняются ограниченные повторы
   с задержкой; после исчерпания — статус failed и возможность явного retry.
8. Транскрипция допускает поступление файлов не по порядку. Анализ договорённостей
   выполняется последовательно по временным окнам звонка с учётом выбранных дорожек,
   а не по sequence_no разных потоков. Использовать границу готовности всех активных
   дорожек и ограниченное ожидание; пропуски и незавершённые окна учитывать явно.
9. Завершение источника закрывает его дорожки и сообщает количество фрагментов
   для каждой, если оно известно. ended_at звонка не означает готовность обработки:
   запись может стать доступной позднее. Финализация ждёт выбранные источники и
   обработку файлов либо по заданной политике отмечает неполноту. Поздние файлы
   автоматически ставят повторную сверку с историей изменений; окончание звонка
   при этом не отменяется. Повторы finish идемпотентны.

Очередь на PostgreSQL достаточна для MVP, Redis/Celery сейчас не вводить.
При падении контейнера задания восстанавливаются из БД. Отдельно измерять
время обработки, длину очереди и отставание: при постоянном поступлении минуты
аудио в минуту средняя производительность worker должна покрывать этот поток.
Для нескольких звонков учитывать сумму всех активных дорожек; ограничивать
параллелизм и распределять задания так, чтобы один источник не блокировал остальные.

## Извлечение задач и управление контекстом

- Отдельный интерфейс LLM-провайдера с проверяемым структурированным результатом.
- Вход: новый фрагмент, хвост предыдущего диалога, подтверждённые участники и
  релевантные открытые поручения. Ограничить токены конфигурацией.
- Не отправлять всю историю звонка на каждом шаге. При переполнении бюджета
  обрабатывать окна последовательно и явно запрашивать дополнительный контекст.
- Различать говорящего и ответственного; учитывать ответ в следующем фрагменте.
- Каждая задача имеет подтверждение в репликах; не выдумывать ответственного,
  срок или завершение. Неясные поручения помечать как требующие проверки.
- Сохранять исходный срок «до завтра»; нормализовать его только при достаточной
  определённости даты, часового пояса и смысла фразы.
- Уточнение существующего поручения обновляет его с историей, а не создаёт копию.
  Технические повторы блокируются ключами обработки; смысловые дубликаты требуют
  отдельного сопоставления, их нельзя решить только уникальным SQL-индексом.
- Ошибка LLM не должна терять уже сохранённую расшифровку.
- Итоговая сверка использует задачи и источники, проходит разговор окнами при
  необходимости; не требует поместить длинный звонок целиком в контекст.

## API и последующий MCP

Сначала реализовать сервисы чтения и HTTP API:

- `POST /audio` — основной вход для кнопки: file и provider, ответ `202` с ID и status_url.
- `GET /meetings/{id}` — состояние звонка, обработки и полноты, включая ошибки.
- `POST /meetings` — явное создание звонка для расширенного сценария; кнопке не нужен.
- Создание источника/дорожки для загрузки; ручной клиент может получить их
  автоматически при создании звонка.
- `POST /meetings/{id}/chunks` — загрузить фрагмент с публичным stream_id.
- `GET /meetings/{id}/chunks/{chunk_id}` — состояние обработки.
- `POST /meetings/{id}/finish` — завершить приём.
- Методы подтверждения человека для спикера и корректировки поручений.
- Получение задач по человеку/звонку/статусу и реплик по временному диапазону.
- На будущем этапе — управление подключениями и подписками; webhook-входы для поддерживающих их
  адаптеров. Workspace определяется аутентификацией/подключением, а не доверенным
  значением из произвольного webhook payload. API/MCP чтение всегда ограничено workspace.

Затем обернуть сервисы чтения в MCP tools: `get_person_tasks`,
`get_meeting_transcript`, `search_meetings`. MCP не предоставляет произвольный SQL.
Перед подключением к ChatGPT сверить действующие требования официальной документации.

Ответы ограничены: для задач — например, 20 записей на страницу и короткие
цитаты; для расшифровки — диапазон времени, лимит и cursor. Возвращать has_more,
источник и статус полноты обработки. Не выдавать ограниченную страницу за все задачи.
При нескольких людях с именем Али возвращать кандидатов для выбора постоянного ID.
На первом этапе поиск по тексту и фильтрам; векторный поиск — последующее расширение.

## Перенос в Supabase

- С самого начала использовать отдельную схему приложения, например `call_summary`,
  с явными правами серверной роли. Не открывать таблицы через Data API автоматически.
- Локальный MVP использует один workspace; принадлежность данных и согласованность
  связей заложить сразу. До удалённого доступа добавить аутентификацию API/MCP
  и членство пользователей в workspace. Для таблиц, доступных через Supabase API,
  включить RLS по членству; серверные запросы также явно ограничивать workspace.
- Подключение Python к Supabase PostgreSQL через DATABASE_URL; SSL и небольшой
  пул соединений. Способ подключения выбрать по окружению; для постоянного
  backend рассмотреть direct или session pooler. Миграции — отдельным соединением.
- Единый S3-адаптер: MinIO сначала, private bucket Supabase Storage позже.
  Настроить endpoint/регион/S3-ключи Supabase, сохранив storage_key; отдельный
  Supabase-only адаптер для аудио не вводить. Перед переключением перенести
  объекты через API и выполнить одинаковые контрактные проверки обоих хранилищ.
- Проверить миграции на пустой целевой БД, затем отрепетировать перенос копии
  данных. При реальном переносе остановить запись, сделать backup и перенести
  только схему/данные приложения и согласованную историю Alembic; не заменять
  системные схемы и роли Supabase.
- Отдельно перенести аудио, проверить ключи, количество записей, связи,
  чтение расшифровок и задачи. Переключить конфигурацию только после проверки;
  сохранить локальную копию и описать возврат до возобновления записи.
- Реальный перенос и размещение контейнеров — отдельный этап после локального MVP.

Официальные ориентиры для этапа переноса:

- [Подключение к Supabase PostgreSQL](https://supabase.com/docs/guides/database/connecting-to-postgres)
- [Перенос PostgreSQL в Supabase](https://supabase.com/docs/guides/platform/migrating-to-supabase/postgres)

## Порядок реализации и приёмка

Модель-исполнитель всех семи specs: **GPT-5.6 Sol** (`gpt-5.6-sol`).
При запуске исполнителя явно выбирать эту модель и соблюдать зависимости этапов.
Это назначение в плане, а не автоматическое переключение модели текущего чата.

Для каждого этапа создан отдельный spec с работами, зависимостями, критериями
приёмки, проверками и артефактами завершения. Spec 01 реализован; остальные specs запланированы.
Создание документов не означает реализацию этапов. Критерии имеют ID `S01-01`
и далее: в отчёте реализации отмечать выполненные, проваленные и невыполненные
проверки с фактическими результатами. Невыполненную проверку не считать пройденной.

1. [Spec 01 — Docker, конфигурация, миграции и модели данных](specs/01-infrastructure-and-data-model.md), включая workspace и источники.
2. [Spec 02 — Структурированная транскрипция и совместимость старого API](specs/02-structured-transcription.md).
3. [Spec 03 — Загрузка по кнопке, очередь и worker](specs/03-upload-and-worker.md): POST /audio (file + provider), общий upload-адаптер,
   автоматическое создание записей, надёжная очередь, worker и восстановление.
   Расширенный приём фрагментов — поверх того же сервиса.
4. [Spec 04 — Сопоставление спикеров, извлечение и исправление задач](specs/04-speakers-and-action-items.md).
5. [Spec 05 — Ограниченные запросы чтения, MCP и документация подключения](specs/05-read-api-and-mcp.md).
6. [Spec 06 — Репетиция переноса в Supabase](specs/06-supabase-migration.md); embeddings — после проверки качества поиска.
7. [Spec 07 — Реальные адаптеры сервисов](specs/07-provider-integrations.md) по одному, с проверкой их возможностей и отдельными
   сценариями приёмки. Сначала заглушки событий, затем подписки/опрос/захват.
   Не считать готовую схему БД работающим захватом звонков.

Обязательные проверки (детальные сценарии и ожидаемые результаты распределены
по таблицам приёмки в specs):

- У каждой таблицы есть уникальный публичный UUID `id` и первичный BIGINT
  `int_id`; все FK ссылаются на `int_id`, JOIN используют внутренние ключи.
- API/MCP принимают и возвращают UUID; после переноса новые identity-значения
  не конфликтуют с существующими записями.
- Чистое окружение поднимается по README; данные переживают перезапуск.
- Инициализация приватного S3-bucket повторяема; API и worker читают/пишут через
  один адаптер без общего аудиотома. Пересоздание контейнеров сохраняет объекты.
- Контракт put/get/head/delete/list с пагинацией проверен на MinIO и отдельно
  на Supabase. Размер и SHA-256 совпадают; ETag не используется вместо хеша.
- Отказ S3/БД при upload и конкурентные retry не оставляют потерянных ссылок,
  не удаляют чужие объекты; orphan-уборка и очистка временных файлов проверены.
- Кнопка отправляет только file + provider; без предварительных API-вызовов
  сервер создаёт звонок и возвращает ID и URL состояния. Все четыре допустимых
  provider работают в режиме upload без подключённых аккаунтов этих сервисов.
- Пропущенный provider даёт manual; неизвестный — 422. Повтор с Idempotency-Key
  не создаёт второй звонок, другой файл с тем же ключом даёт 409.
- Два запроса без ключа/meeting_id с одинаковым provider создают разные звонки;
  продолжение с сохранёнными ID попадает в исходный звонок.
- Загрузка законченного файла автоматически запускает финализацию; is_final=false
  оставляет поток открытым. Метка provider не изменяет серверного ASR-провайдера.
- Три последовательных фрагмента дают один звонок и правильную хронологию.
- Дубликаты и конкурентная загрузка не создают повторных записей; конфликт даёт 409.
- Два звонка в одной комнате остаются разными; переподключение адаптера не создаёт
  копию текущего звонка. Неизвестный внешний сеанс получает устойчивый ключ.
- Две дорожки одного звонка одновременно принимают sequence_no=0 без конфликта;
  после сброса нумерации новая дорожка сохраняет правильные временные смещения.
- Повтор webhook и повтор после перезапуска дают одно событие, один сеанс и одно
  задание; поздний start не отменяет end. Истечение подписки и восстановление
  курсора проверяются на заглушке провайдера.
- Одно имя в разных сервисах не объединяет людей; подтверждённые аккаунты одного
  человека позволяют получить его задачи со всех источников в текущем workspace.
- Несколько входов участника сохраняются; список присутствующих не используется
  как доказательство соответствия голоса человеку в смешанной записи.
- Повторный импорт смешанной и раздельных записей не дублирует задачи;
  финализация учитывает задержанный файл и неизвестное число фрагментов.
- Доступ и составные FK не допускают смешивания данных двух workspace.
- Worker восстанавливается после падения; устаревший worker не перезаписывает результат.
- Проверены файлы не по порядку, пропуски, пустая речь и ошибка провайдера.
- Поручение и согласие на границе файлов дают одну задачу с источниками.
- Смена срока и отмена сохраняют историю; неизвестный спикер не становится Али.
- Повтор анализа не размножает задачи; сбой анализа не теряет текст.
- Вопрос о задачах возвращает поручения, цитаты и пагинацию без всей расшифровки.
- На репрезентативном наборе проверить планы основных SQL-запросов и нагрузку
  поступления одного фрагмента в минуту; записать измерения, не обещать задержку заранее.
- Интеграционные тесты используют PostgreSQL и заглушки внешних провайдеров;
  реальную транскрипцию проверить отдельным небольшим smoke-тестом.
- Приложить инструкции запуска, восстановления, резервного копирования и переноса.
