# Архитектура и правила работы над call_summary

## Назначение и состояние проекта

Проект принимает аудио звонков, сохраняет структурированную расшифровку,
извлекает поручения и предоставляет ограниченные запросы через MCP.
Согласованная целевая архитектура описана ниже; это не утверждение, что она
уже реализована. Перед работой проверить фактический код и состояние миграций.

Spec 01 реализован: Compose, схема из 19 таблиц, Alembic 0001, S3-адаптер,
readiness и placeholder worker. Результаты: [отчёт S01](docs/spec01-verification.md).
Ключи принадлежности в БД неизменяемы; атрибуция человека/спикера редактируема.
Рабочий `/audio` и обработка jobs пока не реализованы (spec 03).

Общий план: [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md).
Работать по соответствующему spec, его зависимостям и критериям приёмки:

## Текущий продуктовый сценарий

- Загрузка по кнопке: `POST /audio`, multipart `file` и `provider`.
- Provider: manual (по умолчанию), google_meet, discord, telegram; неизвестный — 422.
  Это происхождение записи, а не выбор ASR/LLM и не авторизация аккаунта сервиса.
- Для upload не нужны OAuth/боты или предварительное создание сущностей клиентом.
  Сервер создаёт workspace-scoped источник, звонок, дорожку, фрагмент и job;
  возвращает 202 с публичными UUID и status_url.
- По умолчанию законченный файл создаёт отдельный звонок. Для сетевого retry
  используется Idempotency-Key: прежний запрос возвращает прежние ID,
  конфликт содержимого — 409. Без ключа одинаковое аудио может быть новой отправкой.
- Будущее продолжение звонка передаёт meeting_id, stream_id, sequence_no,
  offset_ms, is_final; один provider не идентифицирует звонок.
- Сохранить совместимость существующего `POST /transcribe` → `{"text": ...}`.

## Компоненты и границы

```text
Клиент / будущие адаптеры → FastAPI → PostgreSQL: сущности и processing_jobs
                                 → S3-адаптер → MinIO / Supabase Storage
Worker → processing_jobs → S3 download → временный файл → VoiceProcessor
       → реплики PostgreSQL → LLM-анализ → задачи + источники + история
ChatGPT → MCP → сервисы чтения → PostgreSQL
```

- Локальный Docker Compose: db, minio, api, worker; одноразовые миграции и
  инициализация приватного bucket. Образы PostgreSQL/MinIO закреплены, без latest.
- PostgreSQL, SQLAlchemy, Alembic; схема call_summary. Alembic — единственная
  история миграций. В MVP нет графовой БД, embeddings, Redis или Celery.
- API принимает запросы, проверяет доступ, валидирует и ставит jobs. Worker
  выполняет тяжёлые сетевые/аудио/LLM-операции с ограниченным параллелизмом.
- Модели загружаются один раз на процесс обработки. Импорт API чтения/MCP не
  загружает ASR. Не блокировать event loop синхронной обработкой или S3-клиентом.
- Python >=3.14 по проекту; проверять реальные зависимости. CPU — базовый режим,
  GPU отдельная конфигурация. Локальный Docker не означает офлайн ASR/LLM.

## Правила данных

- Каждая таблица, включая связующие и будущие: `id UUID NOT NULL UNIQUE
  DEFAULT gen_random_uuid()` и `int_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY`.
- UUID используются в API/MCP; BIGINT — во всех FK и JOIN. FK вида meeting_id
  внутри БД ссылаются на int_id, хотя одноимённое поле внешнего API содержит UUID.
- Workspace определяет принадлежность данных. Использовать составные FK и JOIN
  по workspace_id и внутренним ключам; root workspace_id ссылается на workspaces.int_id.
  Проверять принадлежность источников/реплик/задач одному звонку также на уровне БД.
- Различать meeting, source_session и audio_stream. Комната не равна звонку;
  reconnect не должен создавать новый звонок. Номер фрагмента уникален в stream.
- Внешние ID сервисов — TEXT с явно заданной областью уникальности. Provider и
  transport разделены: upload и integration — разные каналы доставки.
- People — люди, person_identities — их подтверждённые аккаунты,
  meeting_participants/participant_sessions — участие и отдельные входы,
  meeting_speakers/chunk_speakers — идентификация речи.
- Одинаковое имя или SPEAKER_00 в разных файлах не доказывает одну личность.
  Ответственный за задачу может отличаться от говорящего.
- TIMESTAMPTZ — календарное время; start_ms/end_ms/offset_ms — шкала звонка.
  Не подменять неизвестное время записи временем загрузки.
- Структуру извлекать до склейки текста в VoiceProcessor. Result_text хранится
  по фрагментам; всю расшифровку собирать из реплик по запросу, не переписывать ежеминутно.

## Аудиохранилище

- Один S3-адаптер для MinIO локально и Supabase Storage после переноса.
  Поддерживать проверенные общие put/get/head/delete/list; list с пагинацией.
- Named volume minio_data подключается только к MinIO; postgres_data — к БД.
  API и worker используют S3 по сети, не общий файловый аудиотом.
- Приватный bucket call-audio. Storage key:
  `<workspace_uuid>/<meeting_uuid>/<stream_uuid>/<chunk_uuid>.<format>`.
  Не хранить endpoint, URL, секреты или абсолютные пути контейнера в ключе.
- Конфигурация: AUDIO_STORAGE_BACKEND=s3, S3_ENDPOINT_URL, S3_REGION, S3_BUCKET,
  S3_ACCESS_KEY_ID, S3_SECRET_ACCESS_KEY, S3_ADDRESSING_STYLE=path, AUDIO_TEMP_DIR.
  Проверять SigV4. Административные credentials MinIO отделены от доступа приложения.
- Worker скачивает объект во временный файл для ASR и удаляет его после обработки.
  Аудиобайты не хранятся в PostgreSQL; там ключ, SHA-256, MIME, длительность и текст.
- Проверять SHA-256 независимо от ETag. Не зависеть от versioning, object lock
  или MinIO notifications. Multipart, если нужен, проверять на обоих endpoint.
- Между S3 и PostgreSQL нет общей транзакции. Нужны компенсация, идемпотентность
  и уборка orphan-объектов с учётом активных загрузок; не удалять объект победившего retry.
- Не выдавать серверные S3-ключи клиенту. Ключи Supabase S3 обходят RLS:
  доступ к объектам проверяется backend по workspace.

## Очередь, анализ и чтение

- Durable queue в processing_jobs, захват FOR UPDATE SKIP LOCKED в короткой
  транзакции, обработка вне неё, lease/heartbeat/token, ограниченные retry.
- Устаревший worker не фиксирует результат. Реплики, статусы и следующее задание
  записываются атомарно. Не считать доставку exactly-once: обеспечивать идемпотентность.
- Учитывать пропуски, приход не по порядку, поздние файлы, неизвестное количество
  фрагментов и альтернативные mixed/per-person записи. Конец звонка не равен
  окончанию обработки; статус полноты показывается явно.
- LLM получает новое окно, хвост контекста, участников и релевантные задачи
  в ограниченном бюджете; не весь архив. Анализ использует реплики БД, не скачивает аудио.
- Поручения имеют источники-реплики; изменения сохраняют историю. Неопределённый
  ответственный/срок остаётся nullable/review. Повтор анализа не размножает поручения
  и не должен тихо перезаписывать ручные исправления.
- MCP tools: get_person_tasks, get_meeting_transcript, search_meetings через
  общие сервисы чтения, без произвольного SQL. Лимиты, cursor, has_more, цитаты,
  временные метки и полнота обязательны. Не выдавать страницу за полный список.
- Чтение сохранённых текстов/задач не зависит от ASR или доступности S3.
  Перед реальным подключением ChatGPT сверить официальную документацию MCP.

## Перенос и будущие интеграции

- Supabase размещает PostgreSQL и Storage, Python API/worker размещаются отдельно.
- Переносить БД и объекты отдельно, сохраняя UUID/int_id/storage_key и историю
  Alembic. После restore восстановить identity-последовательности.
- Аудио копировать MinIO → Supabase через API с проверкой ключей/размеров/SHA-256.
  Замена endpoint не переносит данные; volume MinIO не является форматом импорта.
- Репетиция на копии, согласованный backup, остановка записи/worker при cutover,
  проверка и план возврата. Не заменять системные схемы/роли Supabase.
- До удалённого доступа нужны аутентификация/членство workspace; RLS для таблиц,
  доступных через Data API, и явные ограничения серверных запросов.
- Реальные сервисы подключаются позже через общий контракт ingestion. Сначала
  заглушки событий, затем проверенные режимы каждого сервиса. Upload остаётся доступен.
- Не предполагать live-аудио по наличию события начала звонка. Каждый провайдер
  отдельно проверяется по актуальной официальной документации и реальному прогону.

## Проверка и отчётность

- При реализации отмечать критерии Sxx-yy соответствующего spec с фактическими
  результатами. Невыполненные проверки не считать пройденными.
- Интеграционные проверки БД — PostgreSQL, S3 — реальный MinIO; не заменять их
  SQLite/одними mocks. ASR/LLM заглушки — для детерминированной логики; отдельный
  реальный smoke/оценка нужны для подтверждения работы внешнего провайдера.
- S3-контракт повторить на Supabase в этапе переноса. Проверить конкуренцию,
  перезапуск, stale lease, изоляцию workspace, временные файлы и orphan-объекты.
- Измерять запросы/очередь на описанном наборе, не обещать неподтверждённую задержку.
- Документировать изменения запуска, восстановления и backup; синхронизировать
  этот файл, общий план и затронутые specs при изменении архитектуры.
- Никогда не добавлять секреты, реальные записи звонков, временное аудио и данные
  volumes в Git. Обычная остановка не удаляет volumes; удаление — явная операция.
- Выполнять запрошенный этап, не объявлять будущие этапы реализованными и не
  запускать все specs лишь потому, что они перечислены в этом файле.
